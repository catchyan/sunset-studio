# 工作室效能指标

> Owner: Q1 闸门官（采集）+ P0 总督（汇报）· 每周更新 · 每里程碑结算
> 章程第 1 条：**工作室本身是产品。** 产品就要有指标。

---

## 0. 为什么不用"速度"做指标

最容易想到的指标是"每周完成多少任务"。它是所有指标里最糟的一个。

它可以被轻易地做漂亮：把任务拆得更碎、挑简单的做、降低完成标准。
而且它奖励的是**产出量**，不是**产出质量**，更不是**下次能不能更快**。

下面这套指标围绕一个问题设计：**这个团队是在积累能力，还是只是在忙？**

---

## 1. 六个核心指标

### M1 · 首次通过率（First-Pass Yield）

> 一次就通过全部闸门、无需返工的 PR 占比。

```
FPY = 首次提交即全绿并合入的 PR 数 / 总 PR 数
```

| 阶段 | 目标 |
|---|---|
| S0（框架成型） | 无目标，只观测 |
| S1（第一款游戏） | ≥ 50%，季度末 ≥ 65% |
| S2 起 | ≥ 75% |

**这是最重要的单一指标。** 它同时反映三件事：任务信封写得清不清楚、Bot 理解得对不对、闸门标准是否稳定。

⚠️ **反向操纵警告**：放松闸门可以让这个数字瞬间变好看。
所以它必须和 M2（缺陷逃逸率）一起看。**FPY 上升同时逃逸率上升 = 闸门被放水了。**

### M2 · 缺陷逃逸率（Escape Rate）

> 已经合入 main、之后才被发现的问题数 / 总合入 PR 数。

来源：红队抽检 FAIL、安灯、规格漂移、人类试玩发现的问题。

| 阶段 | 目标 |
|---|---|
| S1 | ≤ 15% |
| S2 起 | ≤ 8% |

每一次逃逸都要写 `board/escapes/<id>.md`，核心问题只有一个：

> **哪道闸门本该拦住它？为什么没拦住？**

答案是"没有哪道闸门覆盖这种情况" → 这是工作室层的收获，去加闸门（且按铁律二，这条改动有真实事故背书）。

### M3 · 周期时间（Cycle Time）

> 从任务状态 `TODO → DONE` 的中位数与 p90。

分别统计：等待时间（TODO→IN_PROGRESS）、执行时间、评审时间（REVIEW→DONE）。

**要盯的是 p90 而不是中位数。** 中位数好看但 p90 很长，意味着存在一类系统性卡死的任务，
而那类任务往往正是关键路径上的。

| 阶段 | p90 目标 |
|---|---|
| S1 | ≤ 2 个工作日 |
| S2 起 | ≤ 1 个工作日 |

### M4 · 人类介入次数（Human Touches）

> 每周人类做出决策、回答问题、手工操作的次数。

**这是工作室成熟度最诚实的指标，也是唯一一个"越低越好且不能被操纵"的指标。**

不能被操纵的原因：Bot 无法通过降低标准来减少人类介入——它只能通过真的把事情做对来减少。

| 阶段 | 目标 |
|---|---|
| S1 | ≤ 15 次/周 |
| S2 | ≤ 8 次/周 |
| S3 | ≤ 4 次/周（基本只剩品味评审与立项） |

⚠️ **不计入**：人类主动发起的改动、品味评审、立项决策。这些是人类的**保留权力**，不是"介入"。
**计入**：Bot 卡住来问、流程走不通要人裁决、环境坏了要人修、Bot 之间吵架要人断。

### M5 · 返工率（Rework Rate）

```
返工率 = 被打回 ≥1 次的 PR 数 / 总 PR 数
```

配套看**返工原因分布**，这比比率本身有用得多：

| 原因 | 说明什么 |
|---|---|
| 需求理解错 | 任务信封第 1/2 段写得不清楚 → **派单方的问题** |
| 越界 | 车道表有歧义 → **架构的问题** |
| 验收不过 | 实现能力问题 → Bot 的问题 |
| 契约对不上 | 契约冻结流程没走好 → **流程的问题** |
| 评审口味 | 评审者夹带私货 → **评审纪律的问题** |

> 注意有四类的根因都不在实现者身上。这正是宪法第二十条"修流程不修人"的数据依据。

### M6 · 新成员上手时间（Onboarding Time）

> 一个新 Bot 从创建，到第一个 PR 合入 main 的时长。

| 阶段 | 目标 |
|---|---|
| S1 | ≤ 1 天 |
| S2 起 | ≤ 4 小时 |

**这个指标直接决定工作室能不能扩张。** 上手要三天，团队就永远只能是现在这么大。

它也是文档质量最好的代理指标：新 Bot 卡在哪里，就是文档在哪里没写清楚。
每次有新 Bot 入职，都要问它一句：**"你读文档的时候，哪一处让你猜了？"** 答案直接变成文档改进任务。

## 2. 跨项目指标（工作室存在的意义所在）

前六个指标衡量"这个项目跑得好不好"。下面两个衡量"**工作室有没有在积累**"。

### X1 · 启动成本（Time to First Playable）

> 从项目 kickoff，到第一个**人类可以真的玩**的垂直切片的天数。

| 项目 | 目标 |
|---|---|
| 第 1 款 | 基线，无目标 |
| 第 2 款 | ≤ 第 1 款的 **50%** |
| 第 3 款 | ≤ 第 2 款的 **70%** |
| 此后 | 不退步 |

**这是章程第 2 条使命的直接度量。达不到，工作室层就是失败的**——无论游戏卖得多好。

### X2 · 复用率（Reuse Ratio）

> 新项目中，来自 `@studio/*` 可复用件的代码与流程资产占比。

配套看**能力账本**（`capability-ledger.md`）的增长：工作室每季度新增了几项"已掌握并可复用"的能力。

⚠️ **不要把复用率当成越高越好的指标。** 高复用率也可能意味着新项目在被旧架构绑架，
做的是同一款游戏的换皮。它需要和"这款游戏有多少是真的新东西"一起读。

## 3. 采集与汇报

| 何时 | 谁 | 做什么 |
|---|---|---|
| 每日 | Q1 | 自动脚本采集 M1/M2/M3/M5 的原始事件 |
| 每周五回顾 | P0 | 汇报六项核心指标 + 趋势，写进 `board/retros/<week>.md` |
| 每里程碑 | P0 | 结算，写进 `board/milestones/<M>.md` |
| 每项目结束 | P0 + 人类 | 结算 X1/X2，写跨项目复盘，更新能力账本 |

**周报只报趋势，不报绝对值。** 单周的绝对值噪声太大，"本周 FPY 62%"没有信息量，
"FPY 连续三周下降，从 71% 到 62%"才有。

---

## 4. 一条使用纪律

**指标是用来发现问题的，不是用来考核 Bot 的。**

一旦某个指标被用于问责，它就会立刻失真——这是古德哈特定律，对 Bot 同样成立（它们会学到"什么样的输出不会挨骂"）。

所以：
- 指标**按项目和阶段汇总**，不按 Bot 排名
- 指标恶化时，第一个问题是"**流程哪里出了问题**"，不是"谁干的"
- 唯一按 Bot 记录的是信任账本，而它记的是**谎报**这类诚信问题，不是效率问题

> 效率低是流程的责任，谎报是个体的责任。**不要把两者混在一起。**
