# RELAY 协作框架

> 状态：ACTIVE v1.0 · 所有者：总督(P0) · 变更需人类批准
> 本文件定义本工作室的多 Agent 协作制度，适用于所有项目。它是为 **Grok Bot 的具体约束**和**能力不稳定的 Agent 群体**量身设计的。

---

## 0. 设计前提：我们面对的到底是什么

在抄任何成熟框架之前，必须先承认三件事，否则抄来的东西一定水土不服。

### 0.1 Grok Bot 的硬约束（来自 xAI 官方文档，2026-08 核查）

| 约束 | 数值 | 对协作设计的影响 |
|---|---|---|
| Bot + 群聊总数上限 | 50 | 编制不是瓶颈，但群聊也占额度，不能滥建群 |
| 单个群聊 Bot 数 | **2–6** | **议事体必须小。**"全员大会"在物理上不存在，只能设分层议事结构 |
| 云电脑 | **全账号共用一台** | 文件、浏览器 cookie、命令行凭证全共享。**并发写冲突是头号风险** |
| 每 Bot 屏幕 | 各自独立，但**同一 Bot 同时只能跑一个 computer-use 任务** | 并行度 = Bot 数量，单 Bot 严格串行 |
| Routine | 每 Bot ≤50 条，保留最近 20 次运行记录，可定时/事件触发 | **这是心跳、巡检、日报的唯一基础设施** |
| Skill | 跨 Bot 共享，`/` 引用，需按 Bot 启用 | **这是固化 SOP 的唯一载体** |
| Bot description | 永久规则；对话 = 一次性指令 | 长期约束写 description，短期任务写消息。写错地方 = 规则失效 |
| 记忆 | Bot 会保留偏好与摘要，但**不是权威数据源** | 一切权威状态必须在 git / 文件里，不能靠 Bot 记 |
| 批准机制 | 逐动作批准 + Auto-review 规则 | 可以把"危险动作"变成强制人类闸门 |

**最关键的一条：所有 Bot 共用一台电脑一个文件系统。** 这一条几乎否定了所有现成框架的默认假设（它们都假设 agent 是无状态函数或各有沙箱）。RELAY 的一半设计量花在这上面。

### 0.2 弱 Agent 的七种典型失效

这是设计的真正靶子。用户的要求原话是"哪怕是一群智商没那么高的 agents 团队，做出来的效果也是可行、可递归优化、可审核的"。翻译成工程语言，就是要把下面七种失效模式各堵死一个：

| # | 失效模式 | 表现 |
|---|---|---|
| F1 | **上下文蒸发** | 换了会话就忘了上周的决定，重新发明轮子或推翻既定设计 |
| F2 | **规格空隙自由发挥** | 任务描述有歧义时不问，自己脑补一个，且脑补得很自信 |
| F3 | **接口幻觉** | 调用不存在的函数、假设不存在的字段、"顺手"改了别人的接口 |
| F4 | **谎报完成** | "我已经实现并测试了"，实际上没跑过 |
| F5 | **越界修改** | 为了让自己的部分能跑，去改了别人的模块，制造隐性耦合 |
| F6 | **静默死循环** | 同一个错误改 8 次，每次都说"这次应该好了"，不求助 |
| F7 | **品味缺失** | 功能齐全，但难看、难用、没有灵魂，且自己看不出来 |

### 0.3 结论

框架必须满足：**产物驱动、契约先行、物理隔离、机器验收、强制求助、人类掌品味、流程自演进。**

## 1. 成熟范式调研与取舍

| 范式 | 核心思想 | 我们取什么 | 我们弃什么 | 理由 |
|---|---|---|---|---|
| **MetaGPT**（`Code = SOP(Team)`） | 把人类软件公司的标准作业流程编码成 Agent 流水线，每个角色产出固定格式的结构化产物（PRD / 设计文档 / API 规格 / 代码 / 测试） | **产物流水线**：每个角色的输出是有固定 schema 的文件，下一环的输入就是上一环的产物。这直接堵 F1、F2 | 弃其**单向瀑布**。一跑到底、不可回头，对我们这种手感驱动的游戏是灾难 | 游戏项目必须能从"手感不对"回退重做，瀑布不允许 |
| **ChatDev** | 虚拟软件公司，CEO/CTO/程序员/测试通过多轮对话推进 | **角色对话作为交接的可见记录** | 弃其**对话即产物**。ChatDev 的结论活在聊天记录里 | 聊天记录不能 diff、不能回滚、不能被 CI 检查。违反第一条留痕原则 |
| **AgileCoder** | Scrum 化：Product Manager / Scrum Master / Developer / Senior Developer / Tester，有 backlog、sprint，backlog 动态更新，并引入代码依赖追踪 | **Sprint 节奏 + 动态 backlog + 代码依赖图**。它在 HumanEval/MBPP 上优于 MetaGPT 和 ChatDev，验证了迭代优于瀑布 | 弃其**角色自组织程度**。它假设 agent 能自主协商，我们不假设 | 我们要为弱 agent 设计，自组织会退化成互相等待 |
| **GitHub Spec Kit** | 宪法 → 规格 → 澄清 → 计划 → 清单 → 任务 → 分析 → 实现 → 收敛，九道闸门，**每一道产出一份可审阅的 Markdown** | **闸门链 + constitution 概念 + `converge` 收敛检查**。这是"可审核"的最佳现成答案 | 弃其**单 agent 假设**。Spec Kit 是给一个 coding agent 用的 | 我们要多 agent 并行，需要额外的所有权与并发制度 |
| **Contract Net Protocol**（1980，Smith） | 管理者广播任务 → 承包者投标 → 授标 → 交付 | **任务招标的思路**用在跨领域任务上（"这个任务谁来接"） | 弃其**竞标机制**。让弱 agent 抢单会导致过度自信者抢走所有活 | 我们改为**总督定向派单 + 接单者有拒绝权**，把"自信"变成"拒绝的理由" |
| **黑板架构（Blackboard）** | 多个知识源读写一块共享黑板，控制器决定谁下一个动 | **`board/` 目录就是黑板**，且它在 git 里，天然可 diff、可回滚、可审计 | 弃其**自由读写**。自由写黑板 = 共享单机灾难 | 改为**分区黑板**：每个 Bot 只能写自己那一格 |
| **丰田生产系统（安灯绳 / A3）** | 任何一线工人都能拉绳停线；问题用一页纸结构化描述 | **安灯绳**（第十三条）与 **A3 式阻塞报告**。这是堵 F6 最有效的机制 | — | 直接采用 |
| **航空业检查单（Checklist）** | 关键动作必须逐条念检查单，不依赖记忆和经验 | **Skill 即检查单**。Grok Bot 的 Skill 机制天生适合承载检查单 | — | 直接采用。这是把"智商"换成"流程"的核心手段 |
| **Google SRE 错误预算 / 事后复盘** | 无指责复盘；改系统不改人 | **第二十条**与信任账本 | 弃其 SLO 数学 | 项目期不需要 |

## 2. RELAY：五条制度

框架名 **RELAY（接力）**。因为在共享单机、单 Bot 串行的条件下，多 Agent 协作的本质就是接力赛——**交接棒的质量决定一切**，而不是每个选手跑多快。

五个字母，五条制度，各堵一组失效模式。

```
R — Record    留痕制    →  堵 F1 上下文蒸发
E — Envelope  信封制    →  堵 F2 规格空隙、F3 接口幻觉
L — Lane      车道制    →  堵 F5 越界修改、共享单机冲突
A — Assert    断言制    →  堵 F4 谎报完成、F7 品味缺失
Y — Yield     让位制    →  堵 F6 静默死循环
```

---

### R · 留痕制（Record）

**规则**：一切结论落盘为 git 文件。聊天只是指针。

| 内容类型 | 落盘位置 | 格式 |
|---|---|---|
| 不可协商原则 | `@studio/docs/00-charter/constitution.md` | 条文 |
| 游戏是什么 | `docs/00-charter/vision.md` | 散文 + 判据 |
| 技术决策 | `docs/02-tech/adr/NNNN-*.md` | ADR（背景/选项/决策/后果） |
| 接口契约 | `docs/02-tech/contracts/*.md` + `packages/protocol/` | Schema + 冻结标记 |
| 玩法规格 | `docs/01-game/*.md` | 规格 + 帧数据表 |
| 当前状态 | `board/` | 结构化 Markdown |
| 完成证据 | `evidence/<task-id>/` | 命令 + 输出 + 截图 |

**执行细节**：
- 每条 git commit 信息格式：`<type>(<scope>): <描述> [<task-id>]`。CI 校验 task-id 存在于 `board/sprint.md`。
- 每个 Bot 每次接手任务，**第一个动作**是 `git pull` 并阅读任务信封列出的输入文件。不允许凭记忆开工。
- 每个 Bot 在结束一次工作会话时，**最后一个动作**是更新自己的心跳文件。

**为什么这条能堵 F1**：Bot 的记忆不可靠，但 `git log` 可靠。把权威状态从模型上下文迁移到文件系统，上下文蒸发就不再致命——重读一遍就恢复了。

---

### E · 信封制（Envelope）

**规则**：任务只能以「任务信封」的形式下达。缺任何一段，接单者必须拒绝。

**任务信封的八段结构**（模板见 `@studio/docs/04-grokbot/skills/sop-task-envelope.md`）：

```markdown
## T-XXX · <标题>

**1. 目标（Why）**
这个任务服务于 <里程碑/规格条目的精确链接>。做完之后，<可观察的变化>。

**2. 输入（Read First）**
- docs/xxx.md#章节
- packages/yyy/src/zzz.ts
（接单者必须先读完这个清单，并在回复第一段确认已读）

**3. 车道（Lane）**
允许修改：packages/sim/src/combat/**
禁止触碰：packages/protocol/**, docs/02-tech/contracts/**

**4. 契约（Contracts）**
必须遵守：docs/02-tech/contracts/combat-events.md v3（FROZEN）
如需变更契约：停手，提 ADR。

**5. 完成定义（DoD）**
- [ ] 实现 X
- [ ] 单测覆盖 Y、Z 两种边界情况
- [ ] 帧数据符合 feel-spec.md 表 3.1

**6. 验收命令（Verify）**
```
pnpm -C packages/sim test -- combat/parry.spec.ts && pnpm lint
```
退出码 0 即通过。

**7. 证据要求（Evidence）**
evidence/T-XXX/ 需含 command.txt / output.txt / diff-stat.txt / parry.gif

**8. 超时与升级（Escalation）**
预计 1 个工作会话。超过 4 小时无进展 → 写 board/blockers/T-XXX.md 并 @总督。
```

**执行细节**：
- **接单者有拒绝权，且拒绝不是过错。** 拒绝时必须说明缺哪一段。
- 第 6 段（验收命令）如果总督写不出来，说明这个任务定义不清，**不是接单者的问题**。
- 第 3 段车道必须与 `@studio/docs/03-gates/ownership-schema.md` 一致，冲突时以所有权表为准。

**为什么这条能堵 F2 和 F3**：F2 的根源是任务有歧义空间；八段结构把歧义空间压到接近零。F3 的根源是不知道接口长什么样；第 2 段强制读、第 4 段强制冻结契约。

---

### L · 车道制（Lane）

**规则**：物理隔离并发，而不是靠自觉。

这是专门为 Grok Bot 共享单机设计的，是本框架相对现成方案最大的增量。

#### L1 · 工作目录隔离（git worktree）

```
/workspace/sunset-club/            # main 的 clone，只读参考，任何人不许在这里改
/workspace/lanes/P0-steward/       # 总督的 worktree，分支 lane/P0
/workspace/lanes/E1-sim/           # 模拟工程师的 worktree，分支 lane/E1
/workspace/lanes/E2-client/        # ...
```

- 每个 Bot **只在自己的 lane 目录里操作**，绝不 `cd` 到别人的 lane。
- 每个 Bot 的分支命名 `lane/<bot-code>/<task-id>`。
- 合入主干只能通过 PR。`main` 设分支保护，禁止直推。

#### L2 · 路径所有权（ownership）

`@studio/docs/03-gates/ownership-schema.md` 是一张 glob → Bot 的映射表，同时生成 `.github/CODEOWNERS`。CI 有一道闸门专门检查 PR 的改动文件是否全部落在提交者的车道内。

**越界不看内容直接拒绝。** 这条必须无情，否则车道制形同虚设。

#### L3 · 全局资源锁（board/locks.md）

共享单机上有些资源天然是全局唯一的：端口、数据库、`pnpm install`、Steam 登录态、浏览器会话。

```markdown
| 资源 | 持有者 | 获取时间 | 预计释放 | 用途 |
|---|---|---|---|---|
| port:2567 | E3-server | 2026-08-20 14:02 | 15:00 | 本地跑权威服调试 |
| pnpm-store | — | — | — | 空闲 |
```

- 获取锁 = 向 `board/locks.md` 追加一行并 commit push。**push 成功者获得锁**（git 天然提供了原子性）。
- 释放锁 = 删除该行并 push。
- 锁超时（超过预计释放 1 小时）→ 总督有权强制回收并记录。

#### L4 · 并发度上限

同一时刻处于 IN_PROGRESS 的任务数 ≤ **活跃 Bot 数**，且同一个 package 内最多 1 个。总督在派单时执行这条。

**为什么这条能堵 F5**：因为 F5 不是道德问题，是能力问题——Bot 想让自己的活能跑，就会去动别人的东西。车道制让它**在物理上做不到**（worktree 隔离）或**在流程上通不过**（CI 越界检查）。

### A · 断言制（Assert）

**规则**：验收由机器执行，Bot 不能自评通过；品味由人类裁决，机器只保底。

#### A1 · 九道闸门（借鉴 Spec Kit，为多 Agent 改造）

| # | 闸门 | 触发 | 执行者 | 通过标准 |
|---|---|---|---|---|
| G1 | **宪法符合性** | 任务派发前 | 总督 | 任务不违反 constitution.md |
| G2 | **规格存在性** | 任务派发前 | 总督 | 任务链接到一条已冻结的规格条目 |
| G3 | **信封完整性** | 接单时 | 接单 Bot | 八段齐全，否则拒绝 |
| G4 | **契约符合性** | PR 打开时 | CI | schema 校验 + 类型检查通过；契约文件无未授权改动 |
| G5 | **车道符合性** | PR 打开时 | CI | diff 全部落在提交者车道内；diff ≤400 行 |
| G6 | **机器验收** | PR 打开时 | CI | 任务卡第 6 段的验收命令退出码 0；单测 + lint + typecheck 全绿 |
| G7 | **手感断言** | PR 打开时（战斗/交互类） | CI | 帧数据快照测试通过；触感六件套 lint 通过 |
| G8 | **同行评审** | CI 全绿后 | 另一个 Bot（非实现者） | 按 `sop-code-review.md` 逐条勾选 |
| G9 | **收敛检查** | 里程碑结束 | 闸门官 + 典藏官 | 代码与规格无漂移；未完成项已回填 backlog |

**外加两道人类闸门**：
- **H1 · 每日 3 条决策**：日报里最多 3 条需要人类拍板的事。
- **H2 · 里程碑品味评审**：人类按 rubric 打分，不过不放行（见 `gates.md`）。

#### A2 · 证据包（Evidence Pack）

见宪法第九条。核心是：**Bot 说"通过了"没用，得把跑的命令和完整输出交出来。**

#### A3 · 红队抽检（Red Team）

闸门官每天随机抽 20% 的 DONE 任务，在**干净的 worktree** 里重跑验收命令。不符即记谎报。

这一条是整个框架的免疫系统。没有它，A1–A2 都可以被"编造输出"绕过。

#### A4 · 信任账本（Trust Ledger）

`board/trust-ledger.md`。见宪法第十条。

它的深层作用是**让闸门自适应**：系统会自动发现"E2 在着色器任务上老是谎报"，于是自动给这类任务加双人复核。这就是"可递归优化"在质量维度的落地。

#### A5 · 品味的可审核化

这是本框架最不像工程、但最重要的一节。用户要求"最好玩最引人入胜"，同时要求"可审核"。这两者的桥是：**把能量化的部分量化到死，剩下的交给人类，并给人类一把标准的尺子。**

三层：

1. **帧数据契约（机器可断言）**：输入延迟 ≤2 帧、命中停顿 3 帧、受击硬直 8 帧、翻滚无敌 9–16 帧……全部写进 `feel-spec.md`，用 headless 回放固定输入序列 + 快照比对来断言。改动导致帧数据变化 → CI 红 → 必须显式更新快照并说明理由。
2. **触感检查单（机器可 lint）**：每个战斗动作必须挂齐屏震 / 命中停顿 / 粒子 / 音效 / 跳字 / 受击闪白。写成内容数据的 schema 必填字段，schema 校验直接卡住。
3. **人类 rubric（人类裁决）**：8 个维度 ×5 分制，里程碑闸门用。见 `gates.md`。

**为什么这条能堵 F4 和 F7**：F4 被 A3 红队直接抓；F7 被第 1、2 层保底（不会难看难用），被第 3 层拔高（好不好由人类说了算，且有尺子，不是玄学）。

### Y · 让位制（Yield）

**规则**：绝不静默，卡住就交出去。

#### Y1 · 心跳（Heartbeat）

每个 Bot 一条 routine，每 2 小时写 `board/heartbeat/<bot-code>.md`：

```markdown
# E1-sim 心跳
- 更新时间: 2026-08-20T14:00+08:00
- 当前任务: T-042 格挡判定
- 进度: 3/5 步（已完成判定窗口与反击触发，剩余音画挂接与单测）
- 最近提交: a3f91c2
- 阻塞: 无
- 下一步: 挂接 parry_success 事件到 VFX 总线
- 预计完成: 今天 17:00
```

#### Y2 · 三振出局（Three Strikes）

宪法第十二条。三次失败必须停手写 A3 式阻塞报告：

```markdown
# T-042 阻塞报告
**目标**：让格挡成功时触发 3 帧命中停顿
**尝试 1**：直接在 combat system 里 setTimeout → 现象：非确定性，回放测试失败
**尝试 2**：用 tick 计数暂停整个 world.step → 现象：远端玩家也被冻结，网络同步炸了
**尝试 3**：只暂停本地渲染插值 → 现象：手感没了，看起来像掉帧
**我的猜测**：命中停顿应该是渲染层概念，不该进 sim；但 feel-spec 把它写在了 sim 的帧数据表里，规格本身可能有问题
**需要谁**：@A1-architect 裁决分层归属
```

注意最后两段——**"我的猜测"和"需要谁"是强制字段**。它把一个弱 agent 的死循环转化成了一条对强 agent 有用的情报。

#### Y3 · 停摆检测（Stall Detector）

总督的 routine，每 3 小时跑一次：

- 心跳超过 3 小时未更新 → 标黄，@该 Bot 追问
- 心跳超过 6 小时未更新 或 IN_PROGRESS 超过 24 小时无 commit → 标红，写进日报的升级区
- 任何 Bot 连续 2 次被标红 → 总督重派该任务，原任务记入回顾

#### Y4 · 安灯绳（Andon）

宪法第十三条。**拉错不罚，不拉才罚。**

#### Y5 · 升级路径

```
实现 Bot
  └─(技术分歧)→ A1 总架构师
  └─(玩法分歧)→ D1 设计总监
  └─(质量分歧)→ Q1 闸门官
  └─(优先级/资源分歧)→ P0 总督
                          └─(总督也定不了 / 涉及愿景或钱)→ 人类（进日报 3 条）
```

每一级必须在 **4 小时内**给出裁决或明确"我也定不了，往上"。**不允许沉默**。

## 3. 组织结构

### 3.1 三层议事体（受 6 人群聊上限约束）

```
                         人类制作人
                              │  (每日 1 份简报 + 最多 3 条决策)
                         ┌────┴────┐
                         │ P0 总督 │  ← 唯一对人类的接口
                         └────┬────┘
        ┌─────────────────────┼─────────────────────┐
        │            【常委会 · 群聊，≤6 席】          │
        │  P0 总督 / A1 架构 / Q1 闸门 / D1 设计       │
        │  + 2 个轮值席（按当前里程碑换人）             │
        └─────────────────────┬─────────────────────┘
                              │
   ┌──────────────┬───────────┴────────┬──────────────┐
【工段群 Cell-A】  【工段群 Cell-B】   【工段群 Cell-C】   （≤4 席，随 sprint 建立与解散）
 实现+评审+P0       实现+评审+P0        实现+评审+P0
```

- **常委会**：常驻群聊，负责跨领域裁决、sprint 规划、回顾。轮值席位机制既满足 6 人上限，又保证当前阶段的关键角色在场。
- **工段群**：一个特性一个群，含实现者、评审者、总督。特性完成即解散（释放额度）。同时最多 3 个。
- **一对一**：日常派单、心跳追问、私下澄清。
- **安灯群**：出事时临时建，含相关方 + P0 + Q1。解决后解散。

额度核算：14 Bot + 1 常委会 + 3 工段群 + 1 安灯群 = **19 / 50**，留足余量。

## 5. 反馈机制总览

用户特别要求"及时知道各个部门进度"。反馈分四个方向，缺一不可：

### 5.1 向上（Bot → 人类）
- **唯一通道**：`board/daily-brief.md`，每天 21:00 由总督生成。
- **格式硬约束**：
  - 一屏内读完
  - 三段：昨日完成 / 今日在做 / 风险与阻塞
  - **需要你决定的事 ≤3 条**，每条含：背景两句 + 选项 + 推荐 + 不决定的后果
- 里程碑时额外一份验收报告 + 可玩构建。

### 5.2 向下（人类 → Bot）
- 人类只对总督说话。总督负责翻译成任务信封并分发。
- 例外：人类可以直接跳过总督下达"停"（宪法允许，紧急制动）。

### 5.3 横向（Bot ↔ Bot）
- 交接：工段群里 @ 对方，附任务信封链接与产物路径。
- 求助：先看是否属于对方车道，属于就 @，不属于就找 P0。
- **禁止**：在群里做长篇技术讨论。超过 3 轮没结论 → 转成 ADR 提案，异步走文件。

### 5.4 向内（系统 → 系统，即递归优化）
这是"可递归优化"的落点，四条自我改进回路：

| 回路 | 输入 | 输出 | 周期 |
|---|---|---|---|
| **SOP 回路** | 回顾中暴露的流程缺陷 | SOP 变更 PR（改 skill 文件） | 每周 ≥1 |
| **闸门回路** | 逃过闸门的缺陷 | 新增一道自动化检查 | 每次线上/主干事故 |
| **信任回路** | 谎报与越界记录 | 对应 Bot 的闸门收紧 / description 重写 | 触发式 |
| **规格回路** | 代码与规格的漂移 | 要么改代码要么改规格，二选一，不许并存 | 每日 S1 检测 |

**判据**：如果连续两周没有产出任何 SOP 变更，说明回顾流于形式，总督记一次过。

## 6. 这个框架为什么对弱 Agent 有效（自检）

| 失效 | 堵它的机制 | 是否物理不可能 |
|---|---|---|
| F1 上下文蒸发 | R 留痕制 + 信封第 2 段强制读 | 部分（可重建） |
| F2 规格空隙自由发挥 | E 信封八段 + G2 规格存在性闸门 + 拒绝权 | 强 |
| F3 接口幻觉 | 契约冻结 + G4 类型检查 + G5 契约文件受保护 | **是**（CI 拦死） |
| F4 谎报完成 | A3 红队抽检 + 证据包 + 禁止自评 | **是**（重跑即露馅） |
| F5 越界修改 | L worktree 隔离 + CODEOWNERS + G5 车道闸门 | **是**（CI 拦死） |
| F6 静默死循环 | Y 心跳 + 三振 + 停摆巡检 + 安灯 | 强（最多损失 3 小时） |
| F7 品味缺失 | 帧数据契约 + 触感 lint + 人类 rubric 闸门 | 部分（人类兜底） |

七条里有三条做到了"物理不可能"，三条做到了"最多损失几小时"，一条靠人类兜底。这就是这个框架能承受"智商没那么高的 agent"的原因：**它不依赖 agent 聪明，只依赖 agent 会读文件、会跑命令、会在卡住时喊人。**
