# SOP · 同行评审（G8）

**何时使用**：被指派为某个 PR 的评审人时。
**前提**：CI 必须已经全绿。**CI 红的 PR 不要评审**，直接退回。
**铁律**：评审人不能是实现者本人（宪法第七条）。

---

## 评审不是找茬，是回答一个问题

> **如果这段代码明天出问题，我看着它能不能搞清楚发生了什么？**

---

## 检查单（逐条勾选，全部勾完才能 Approve）

### A. 任务符合性
- [ ] 实现的是任务信封第 1 段说的那件事，不多不少
- [ ] DoD 每一条都真的做到了（不是"看起来做到了"）
- [ ] PR 描述里的"我没做什么"一节写了，且合理

### B. 车道与契约
- [ ] diff 全部落在实现者的车道内（CI 的 G5 已查，但我再扫一眼文件列表）
- [ ] 没有改动任何 FROZEN 契约文件
- [ ] 没有"顺手"修改无关文件（包括格式化整个文件——那会淹没真实改动）

### C. 架构原则（对照 architecture.md §3）
- [ ] `packages/sim` 没有 import DOM / Three.js / 网络 / fs
- [ ] 没有引入非确定性（`Math.random()` / `Date.now()` / 依赖遍历顺序）
- [ ] 表现层没有反向修改 sim 状态
- [ ] 依赖方向正确，没有制造环

### D. 数据驱动
- [ ] 没有硬编码的数值（应该在 `packages/content`）
- [ ] 没有硬编码的中文字符串（应该走 i18n key）

### E. 手感（战斗/交互类才检查）
- [ ] 帧数据与 `feel-spec.md` 及 `frames/*.json` 一致
- [ ] 触感六件套齐全（屏震/命中停顿/粒子/音效/跳字/受击闪白）
- [ ] 没有引入可能破坏 ≤2 帧输入响应的东西（同步阻塞、大对象分配、主循环里的 await）

### F. 可读性
- [ ] 函数名和变量名说的是**做什么**，不是**怎么做**
- [ ] 没有解释"这行代码在干嘛"的废话注释
- [ ] 有注释的地方，注释说的是**为什么这样写**（约束、权衡），而不是**改了什么**
- [ ] 复杂逻辑有对应的测试作为可执行文档

### G. 证据
- [ ] `evidence/T-XXX/` 完备
- [ ] `output.txt` 最后一行是 `EXIT_CODE=0`
- [ ] 视觉/手感类附了截图或录屏，且录屏里真的能看出效果

### H. 我自己跑一遍
- [ ] 我在自己的 lane 里 checkout 了这个分支，**真的跑了一次验收命令**
- [ ] （视觉/手感类）我真的看了 / 玩了

> H 是最容易被跳过的一条，也是最重要的一条。
> 不跑就 Approve，等于把 G8 变成橡皮图章，红队迟早会发现。

## 反馈的写法

分三类，**必须明确标注类别**：

| 标记 | 含义 | 是否阻塞合并 |
|---|---|---|
| `[BLOCK]` | 必须改，否则不能合并 | 是 |
| `[SUGGEST]` | 建议改，实现者可以说不 | 否 |
| `[QUESTION]` | 我没看懂，请解释 | 解释清楚即可 |

**`[BLOCK]` 必须引用具体依据**：宪法条款、契约、规格、闸门条款、架构原则中的某一条。

> ❌ 反例：`[BLOCK] 这里写得不好，改一下`
> ✅ 正例：`[BLOCK] 违反 architecture.md §3.2 确定性：这里用了 Date.now()，请改用 world.tick`

**没有依据的意见只能是 `[SUGGEST]`。** 这条纪律保护实现者不被主观偏好折腾。

---

## 三条评审纪律

1. **不要重写别人的代码。** 指出问题，让实现者改。你直接改了，就没人从错误里学到东西，而且违反车道制。
2. **不要在评审里扩大范围。** "顺便把那个也重构一下吧"——不行，开新任务。
3. **一次说完。** 不要挤牙膏式评审（改完一轮又提新的）。第一轮就把所有 BLOCK 列全。

---

## Approve 之后

1. 在 `board/tasks/T-XXX.md` 里记录：评审人、评审时间、勾选完成
2. 合并（squash merge，保留 `[T-XXX]` 在标题里）
3. 把任务状态改为 `DONE`
4. 如果这个 PR 让你发现了某个闸门的漏洞（CI 该拦没拦） → @闸门 Q1，写 `board/escapes/`
