# SOP · 阻塞报告（Three Strikes）

**何时使用**：同一个问题连续 3 次尝试失败时。**这是强制的，不是可选的。**
**输出**：`board/blockers/T-XXX.md`
**之后**：把任务状态改为 `BLOCKED`，@ 升级路径上的对应角色。

---

## 为什么是三次

弱 Agent 最常见也最昂贵的失效模式是**静默死循环**：同一个错误改 8 次，每次都说"这次应该好了"。
三次是一个经验阈值——三次都不行，说明你缺的不是耐心，是**信息或权限**。
第 4 次相似的尝试是被明令禁止的。

**写阻塞报告不是失败，是把一次死循环转化成一条对别人有用的情报。**

---

## 格式（借鉴丰田 A3，字段不许省）

```markdown
# T-XXX 阻塞报告

- 报告人: <代号>
- 日期: 2026-08-20
- 卡住时长: 3 小时 20 分

## 目标
<一句话：我本来要做到什么。用可观察的结果描述，不是"实现 X 功能">

## 尝试 1
- 做法: <具体做了什么>
- 结果: <具体现象。贴报错原文，不要转述>
- 为什么我以为它会成功: <你的原始假设>

## 尝试 2
- 做法:
- 结果:
- 相比尝试 1 我改变了什么假设:

## 尝试 3
- 做法:
- 结果:
- 相比尝试 2 我改变了什么假设:

## ★ 我的猜测
<必填。你觉得真正的原因可能是什么？哪怕不确定也要写。
 一个弱 Agent 的猜测，往往包含了对强 Agent 极有价值的现场信息。>

## ★ 我需要谁
<必填。@具体的角色，说明你需要他做什么决定或给什么信息。
 不要写"需要帮助"，要写"需要 @架构 裁决命中停顿属于 sim 还是渲染层"。>

## 已排除的可能
<你确认不是原因的东西，帮别人省时间>

## 现场
- 分支: lane/XX/T-XXX
- 最后 commit: <hash>
- 复现命令: <一条能复现问题的命令>
- 相关日志: evidence/T-XXX/blocker-logs/
```

---

## 「我的猜测」和「我需要谁」为什么是强制字段

这两段是整个 SOP 的价值所在。

- 没有「我的猜测」：报告只是"我不会"，接手的人要从头调查。
- 有「我的猜测」：哪怕猜错了，也告诉了接手的人**你的思路走到哪一步、在哪里断的**，这本身就是排除法。

- 没有「我需要谁」：报告变成向全世界喊救命，没人认领。
- 有「我需要谁」：变成一个有明确收件人的请求，4 小时内必须有答复（升级路径的约定）。

---

## 升级路径

```
实现 Bot
  ├─ 技术分歧（架构、接口、依赖、性能） ─────> @架构 A1
  ├─ 玩法分歧（手感、数值、乐趣、可读性） ───> @设计 D1
  ├─ 质量分歧（闸门、验收、证据、标准）  ───> @闸门 Q1
  ├─ 环境/工具问题（依赖装不上、CI 挂了）  ─> @运维 O1
  ├─ 文档矛盾（两处规格打架）           ───> @典藏 S1
  └─ 优先级 / 资源 / 说不清属于谁      ───> @总督 P0
                                            └─> 人类（进日报 3 条）
```

**每一级必须在 4 小时内给出裁决，或明确说"我也定不了，往上"。不允许沉默。**

---

## 阻塞解除后

1. 在报告末尾追加一节：

```markdown
## 解除
- 日期:
- 真正的原因: <与"我的猜测"对比，猜对了还是猜错了>
- 解法:
- 谁解决的:
- ★ 应该新增/修改哪条 SOP 或闸门，让下次不再发生?
```

2. 最后一条是**必答**的。它会进入本周回顾，可能变成一条 SOP 变更 PR。
   这就是"递归优化"的具体落地——**每一次卡住，都要让系统变强一点。**
