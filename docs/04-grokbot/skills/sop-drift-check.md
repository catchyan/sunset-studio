# SOP · 规格漂移检测（Drift Check）

> 执行者：S1 典藏官 · 每日 14:00（routine R6）
> 输出：`board/drift.md`
> 宪法第十条：**代码与规格不一致时，要么改代码，要么改规格，不许两者并存。**

---

## 1. 漂移是怎么产生的

没有人故意制造矛盾。它是这样长出来的：

> D1 在 `feel-spec.md` 里把翻滚无敌帧从 4–16 改成 4–14。
> E1 那天在做别的任务，没看见。
> 三周后 E2 做闪避特效，去读 `packages/content/` 里的 JSON，看到的是 16。
> 又过两周，有人发现文档和数据不一致，但已经没人记得哪个是对的了。

到那个时候，这个矛盾的修复成本是原来的十倍——因为要先做考古。

**S1 的价值不在于修复矛盾，在于把发现矛盾的时间从"三周后"压缩到"当天"。**

## 2. 三类检测

### A. 代码/数据 vs 规格

| 规格文件 | 对应数据 | 检测方式 |
|---|---|---|
| `feel-spec.md §3` 命中停顿表 | `packages/content/combat/hitstop.json` | 逐行比对帧数 |
| `feel-spec.md §4` 帧数据表 | `packages/content/combat/frames/*.json` | 逐字段比对 |
| `feel-spec.md §1` 全局指标 | CI 里的实际断言阈值 | 提取常量比对 |
| `architecture.md §6` 性能预算 | CI bench 的阈值 | 提取常量比对 |
| `gdd-economy.md` 公式系数 | `packages/content/economy/*.json` | 比对 |
| `contracts/*.md` 字段表 | `packages/protocol/src/**` Zod 定义 | 字段名与类型比对 |
| `art-bible.md` 数值规格 | `tools/art-lint` 的阈值 | 比对 |

这一类**应该尽可能自动化**。S1 的长期目标是把每一条都变成 CI 检查，然后自己不用再看。

> **判断标准**：某条检测连续 4 周没抓到任何东西，说明它要么已经被 CI 覆盖了，要么本来就不会漂移。
> 从每日清单里删掉，写进 `board/drift.md` 的"已退役检测"。**清单越短越有人真的看。**

### B. 文档 vs 文档

重点交叉对：

```
gdd-core.md  ←→  feel-spec.md        （机制描述 vs 帧数据）
gdd-core.md  ←→  gdd-economy.md      （产出物 vs 经济投放）
gdd-economy.md ←→ architecture.md    （审计需求 vs 数据库设计）
art-bible.md ←→  architecture.md §5  （美术规格 vs 渲染管线）
roadmap.md   ←→  各里程碑放行条件引用的规格章节是否存在
roles.md     ←→  ownership.md        （职责 vs 车道，最容易漂）
gates.md     ←→  .github/workflows/  （闸门定义 vs 实际 CI）
```

最后两对尤其要盯。`roles.md` 说某个 Bot 负责某事，但 `ownership.md` 里那个路径归了别人——这会导致任务永远派不出去，而症状看起来像"这个 Bot 不干活"。

### C. 术语一致性

对照 `@studio/docs/00-charter/glossary.md`，扫描全部 `.md` 与代码注释。

对照表由项目在 `board/drift.md` 维护：

| 正确 | 常见误用 |
|---|---|
| *（项目填充）* | |

**填表的方法**：每次在评审或文档里发现有人用了同义词，就往表里加一行。
不要一开始凭想象列满——凭想象列的词多半不会被误用，真正会被误用的那些，
要等它第一次发生才知道。

**术语漂移不是文字洁癖问题。** 当一份文档里同时存在两个指向同一事物的词，
新加入的 Bot 会花时间猜它们是不是同一个东西，猜错了就写错代码。
术语表的唯一目的是**消除猜测**。

## 3. 处理流程

```
S1 发现 → 记入 board/drift.md（状态 OPEN）
        → @规格所有者 + @实现方，说明矛盾的两处原文
        → 24 小时内必须有一方给出裁决："以 X 为准"
        → 裁决方改文件，S1 确认后标 RESOLVED
        → 超过 48 小时 → 标 ESCALATED，@总督，进日报风险区
```

### S1 能做和不能做的

| S1 能做 | S1 不能做 |
|---|---|
| 发现并记录矛盾 | **决定哪边是对的** |
| 判断哪份文档是规格所有者 | 直接改规格内容 |
| 修正纯术语错误（改词不改意） | 修正数值（哪怕"明显"是笔误） |
| 要求 24 小时内裁决 | 超时后自行裁决 |

第二列第三行值得强调：**看起来明显的笔误也不许自己改。**

`feel-spec` 写 16、JSON 写 14，S1 觉得"肯定是 JSON 忘了同步"——但也可能是 D1 上周口头调整过而忘了改文档。S1 自作主张改成 16，就把一个可见的矛盾变成了一个隐形的错误。**可见的矛盾是资产，隐形的错误是负债。**

## 4. 每周小结

回顾会上，S1 汇报：

| 指标 | 意义 |
|---|---|
| 本周新增漂移数 | 上升 = 沟通出问题了 |
| 平均消除时长 | > 24 小时 = 责任方不明确 |
| ESCALATED 次数 | > 0 = 有人在拖 |
| **重复漂移的位置** | 同一处反复漂 = 那里的所有权划分有问题，该拆分或合并 |
| 转化为 CI 检查的检测数 | 这是 S1 真正的产出指标 |

最后一行是关键。**S1 的成功标志是自己越来越闲**——因为所有能自动化的检测都自动化了，人工清单越来越短。

如果一年后 S1 还在每天手工比对帧数据表，那说明这个岗位失败了。
