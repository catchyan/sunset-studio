# SOP · 美术资产管线（程序化 / AI 生成）

> 执行者：V1 视效官（主）· E2 客户端（集成）· Q1（G7 闸门）
> 规格来源：`docs/01-game/art-bible.md`
> 工具：`tools/asset-gen/`（生成）+ `tools/art-lint/`（机检）

---

## 1. 这条管线要解决的根本矛盾

我们选了 `proc_ai` 路线：资产靠程序化生成与 AI 辅助，不靠人手绘。

好处是产能。**代价是风格会散。** AI 生成十个敌人，会得到十种画风；程序化生成的地牢，每一间房都"技术上正确"但整体看起来像随机拼的。

3D 像素风尤其脆弱——它的美感几乎完全来自**克制与一致**：固定的调色板、固定的像素密度、固定的光照方向。任何一处破例，整个画面立刻变得廉价。

所以这条管线的核心不是"怎么生成"，是**"怎么让不合格的东西进不来"**。

---

## 2. 三层防线

```
第 1 层：约束生成    —— 生成时就限制在规格内（最有效）
第 2 层：机器 lint   —— art-lint 自动拒收（G7 闸门，不可绕过）
第 3 层：人类品味    —— 里程碑 H2 评审（最贵，只用在机器判不了的地方）
```

**能在第 1 层解决的，绝不留到第 2 层。** 每一条 lint 规则被触发，都说明生成环节的约束不够紧。

### 第 1 层的具体做法

| 手段 | 说明 |
|---|---|
| **调色板强制** | 生成后一律做最近邻量化到 `assets/palettes/sunset-40.png` 的 40 色。不是"建议用"，是管线里的必经步骤 |
| **固定光照方向** | 所有资产在同一套光照设置下烘焙/生成。左上 45° |
| **纹素密度锁定** | 见 art-bible。角色 / 道具 / 场景各有固定的每单位纹素数，生成时按尺寸自动推算贴图分辨率 |
| **模板化 prompt** | AI 生成时用固定的风格前缀 + 固定的负面词。前缀存在 `tools/asset-gen/style-prompt.txt`，**改它需要 V1 批准** |
| **参考图锚定** | 每一类资产有一张"基准图"，生成时作为 reference 输入 |

## 3. 单个资产的完整流程

```
1. V1 从任务信封读需求（尺寸类别、用途、情绪基调）
2. 用 tools/asset-gen 生成 3–5 个候选
   ★ 必须 ≥3 个。只生成一个，你就只能接受它
3. 全部跑 art-lint，淘汰不合格的
4. V1 从合格候选中挑 1 个，写选择理由（一句话）
5. 落盘到 assets/<类别>/，同时写元数据 JSON
6. 在 packages/content/ 中引用它
7. 提 PR，证据包含：候选对比图 + lint 输出 + 在游戏内的截图
```

### 第 7 步为什么必须有"游戏内截图"

资产在 Blender 里好看、在预览图里好看，都不算数。

3D 像素风的特殊性在于：最终画面经过了**低分辨率渲染 + 顶点吸附 + 调色板量化 + 抖动**四道后处理。一个在原始分辨率下精致的模型，量化之后可能糊成一团。

**唯一有效的验收视角，是 384×216 渲染目标里的实际像素。** 其他任何预览都是自我安慰。

## 4. art-lint 检查项（G7 闸门，全自动）

| # | 检查 | 判据 |
|---|---|---|
| 1 | 调色板 | 所有像素必须在 40 色内，容差 0 |
| 2 | 纹素密度 | 与该类别规格的偏差 ≤ 10% |
| 3 | 三角面数 | 不超过该类别预算 |
| 4 | 贴图尺寸 | 2 的幂，且不超过类别上限 |
| 5 | 命名规范 | `<类别>_<语义>_<变体>`，全小写 snake_case |
| 6 | 元数据完整 | 元数据 JSON 存在且字段齐全 |
| 7 | 无孤儿资产 | 落盘的资产必须被 `packages/content/` 引用 |
| 8 | 无重复 | 与现有资产的感知哈希距离 > 阈值（防止生成一堆近乎一样的东西） |
| 9 | 缩略图 | 必须附 384×216 下的实际渲染缩略图 |
| 10 | **强调色纪律** | 见下 |

### 第 10 条：强调色纪律

项目的美术圣经会规定：调色板中有几个**高饱和强调色**，它们**只允许用于玩法反馈**（命中闪白、可防御预警、状态提示、掉落物高亮）。

场景、角色、UI 一律不许使用这几个色。

理由：玩家的注意力资源极其有限。如果强调色到处都是，它就不再"强调"任何东西——玩家会漏掉关键预警，然后觉得游戏不公平。

**这是一条美术规则，但它服务的是玩法可读性。** lint 会逐像素检查。

## 5. 程序化生成（地牢、装饰、变体）

| 原则 | 说明 |
|---|---|
| **种子可复现** | 所有生成用固定 seed，seed 写进元数据。任何人能重新生成出一模一样的结果 |
| **参数在数据里** | 生成参数存 `packages/content/`，不写死在生成器代码里 |
| **产物入库** | 生成结果**提交进 git**，不在运行时生成。理由：运行时生成 = 不可审计、不可 lint、玩家机器上可能不一样 |
| **手工修补允许，但要记录** | V1 可以手工调整生成结果，但必须在元数据里标 `hand_touched: true` 并说明改了什么 |

最后一条的意义：如果某一类资产的 `hand_touched` 比例超过 30%，说明**生成器的约束不对**，应该去改生成器而不是一直手工修。这个比例是 V1 每周要汇报的指标。

## 6. 什么留给人类判断

机器能判"合不合规"，判不了"好不好看"，更判不了"对不对味"。

留给里程碑 H2 评审的问题（见 `gates.md`）：

- 这套资产放在一起，像不像**一个世界**？
- 角色传达出项目题材要求的那种气质了吗？
- 场景有没有题材要求的那种层次感？
- 有没有哪个资产**太抢戏**，抢走了本该给玩法反馈的注意力？

> 第二条通常是每个项目最难也最重要的美术命题：题材气质与"看起来只是画得不好"之间，往往只隔一线。
> 举个例子：某个项目想做"磨损但挺拔"，稍偏一点就变成"破烂"。
> 这个分寸机器判不了，每次里程碑必须人类看。
>
> 项目应在自己的美术圣经里，用**一组正例/反例对照图**把这条线画出来。
> 只写形容词是没用的（宪法第九条：不用形容词交付规格）。

## 7. 资产预算（防止无限膨胀）

每个里程碑开始时，V1 与 D1 商定资产清单并**冻结数量**。

超出清单的资产需求 → 走变更流程，且必须回答："删掉哪一个来换？"

理由：AI 生成的边际成本接近零，这会诱使团队不断加东西。而资产数量每增加一倍，风格一致性的维护成本增加不止一倍，玩家的认知负担也会上升。

**宪法第十八条同样适用于美术：删除的权力。**
每次里程碑收敛，V1 必须提名至少一个"可以删掉的资产"。
