# SOP · 任务信封（Task Envelope）

**何时使用**：总督派发任何任务时；任何 Bot 接到任务时。
**所需权限**：读 `board/sprint.md`、写 `board/tasks/`（仅总督）。

---

## 派单方（总督）：写信封

任务卡存 `board/tasks/T-XXX.md`。**八段缺一不可。**

```markdown
# T-XXX · <一句话标题>

- 状态: TODO
- 负责人: @<Bot 代号>
- 评审人: @<另一个 Bot 代号>（不能是负责人自己）
- 里程碑: M1
- 对应放行条件: <roadmap.md 里的具体那一条>

## 1. 目标（Why）
服务于 <规格文件路径#章节>。
做完之后，可观察的变化是：<具体、可验证的描述>。

## 2. 输入（Read First）
接单者必须先读完这些，并在回复第一段确认已读：
- <精确路径#章节>
- <精确路径>

## 3. 车道（Lane）
允许修改：`<glob>`
禁止触碰：`<glob>`
（必须与 docs/03-gates/ownership-schema.md 一致）

## 4. 契约（Contracts）
必须遵守：`<契约文件路径>` v<N>（FROZEN）
如需变更契约：**停手**，按 /sop-adr 提 ADR，不要自己改。

## 5. 完成定义（DoD）
- [ ] <可勾选的具体项>
- [ ] <可勾选的具体项>
- [ ] 触感六件套齐全（如果是战斗动作）
- [ ] 帧数据与 packages/content/combat/frames/*.json 一致（如果涉及帧数据）

## 6. 验收命令（Verify）
```bash
<一条或多条命令，串联执行，退出码 0 即通过>
```

## 7. 证据要求（Evidence）
`evidence/T-XXX/` 需含：
- command.txt · output.txt · diff-stat.txt
- <视觉/手感类另附>：screenshot.png / clip.gif

## 8. 超时与升级（Escalation）
预计 1 个工作会话。
超过 4 小时无进展 → 按 /sop-blocker 写 board/blockers/T-XXX.md 并 @总督。
```

### 派单前的自检（总督必答）
1. **我自己能跑通第 6 段的验收命令吗？** 跑不通就不许派——那是我的问题，不是接单者的。
2. 第 3 段的车道与所有权表一致吗？
3. 第 4 段引用的契约是 FROZEN 状态吗？还是 DRAFT？DRAFT 状态不能派实现任务。
4. 这个任务推进了哪条里程碑放行条件？答不出就不派。
5. 评审人和负责人是不是同一个？是的话重新指定。

---

## 接单方：签收流程

### 第 1 步 · 检查信封（有权拒绝）
逐条核对八段是否齐全、清楚。缺任何一段 → **拒绝接单**，回复：

> 拒绝接单 T-XXX。缺失第 N 段：<具体缺什么>。请补齐后重新派发。

**拒绝不是过错。** 接了一个定义不清的任务然后自由发挥，才是过错。

### 第 2 步 · 三句自检（回复的第一段必须写）
1. 我读了哪些文件？（列出第 2 段的全部路径，逐条确认已读）
2. 我这次允许改哪些路径？（复述第 3 段的 glob）
3. 我的验收命令是什么？跑通它意味着什么？

### 第 3 步 · 拉取与建分支
```bash
cd /workspace/lanes/<你的 lane>
git fetch origin && git rebase origin/main
git switch -c lane/<你的代号>/T-XXX
```

### 第 4 步 · 先跑一次验收命令
**在写任何代码之前，先跑一次第 6 段的命令。** 它现在应该是失败的（红）。
如果它现在就是绿的，说明这个任务要么已经做完了，要么验收命令写错了 → 回退给总督。

### 第 5 步 · 实现
- 小步提交，每次提交信息带 `[T-XXX]`
- diff 总量控制在 400 行以内。快超了 → 停下来，@总督申请拆分
- 遇到必须改车道外文件的情况 → **停手**，在群里请求授权，不要偷偷改

### 第 6 步 · 自验
```bash
<第 6 段的验收命令>
```
必须真的跑，必须看到退出码 0。

### 第 7 步 · 证据包
按 /sop-evidence-pack 生成 `evidence/T-XXX/`。

### 第 8 步 · 开 PR
```bash
git push -u origin lane/<代号>/T-XXX
gh pr create --title "<type>(<scope>): <描述> [T-XXX]" --body "<见下>"
```

PR 描述模板：
```markdown
## 任务
board/tasks/T-XXX.md

## 做了什么
<3–5 条，写"改变了什么行为"，不要写"改了哪些文件">

## DoD 勾选
- [x] ...

## 验收命令与结果
```
<命令>
<最后 10 行输出，含退出码>
```

## 证据
evidence/T-XXX/

## 我没做什么（范围外）
<明确列出发现但故意没做的事，避免评审者以为漏了>
```

### 第 9 步 · 更新状态
- 改 `board/tasks/T-XXX.md` 的状态为 `REVIEW`
- 在工段群里 @评审人
- **不要说"已完成"。说"待评审"。** 你无权宣布自己通过（宪法第七条）。

### 第 10 步 · 心跳
更新 `board/heartbeat/<代号>.md`。

## 状态机

```
TODO ──接单──> CLAIMED ──开工──> IN_PROGRESS ──开PR──> REVIEW ──合并──> DONE
                  │                   │                  │
                  └──拒绝──> TODO      ├──卡住──> BLOCKED  └──打回──> IN_PROGRESS
                                      └──撤回──> TODO
```

| 状态 | 谁能改成这个状态 | 前置条件 |
|---|---|---|
| TODO | 总督 | 八段齐全 |
| CLAIMED | 接单者 | 通过三句自检 |
| IN_PROGRESS | 接单者 | 已建分支，已跑过一次验收命令（红） |
| REVIEW | 接单者 | CI 全绿 + 证据包完备 |
| BLOCKED | 接单者 | 已写 board/blockers/T-XXX.md |
| DONE | **CI + 评审人**（不是接单者） | G4–G8 全过 |
| REJECTED | 评审人或闸门官 | 引用了具体的闸门条款 |
