# SOP · Sprint 规划

> 执行者：P0 总督主持 · 参与：A1、Q1、D1 + 本 Sprint 相关实现方
> 每周一 · 常委会群聊 · **控制在 30 条消息内**
> 输出：`board/sprint.md` 更新 + 一批 `board/tasks/T-XXX.md`

---

## 1. 唯一的规划原则：从放行条件倒推

**不许问"这周我们做点什么"。** 这个问题会得到一堆听起来都有道理的事情。

要问的是：

> **当前里程碑的放行条件里，哪一条离达成最远？**

然后本周所有任务，都必须能追溯到某一条放行条件。追溯不到的任务，不许进 Sprint——无论它听起来多有价值。

这条规则的作用是**防止里程碑无限膨胀**。弱 Agent（和人）都有一个共同倾向：做那些容易做、看得见成果、但不在关键路径上的事。放行条件倒推是唯一的解药。

## 2. 会议流程（严格按序，30 条消息内）

### 第 1 步 · P0 报告状态（1 条消息）

```
本周 Sprint 规划。M<N> 放行条件进度：<X>/<Y>

已达成：
- <条款原文>

未达成，按"距离"排序：
1. <条款原文> — 差什么
2. <条款原文> — 差什么
3. <条款原文> — 差什么

上周未完成任务：T-0XX（原因：...）
当前 OPEN 安灯：无
```

### 第 2 步 · 逐条认领（每人 1–2 条）

对排名前 3 的未达成条款，相关方回答：

```
条款 <N>：我认为需要拆成 <M> 个任务。
风险：<最可能卡住的地方>
依赖：需要 <谁> 先完成 <什么>
```

### 第 3 步 · A1 检查契约（1 条消息）

**这一步不许跳过。**

```
本周任务涉及的契约：
- <契约名> — 状态 FROZEN ✅ 可以派
- <契约名> — 状态 DRAFT ❌ 不可派实现任务
  → 本周先做契约冻结，实现放下周
```

契约是 DRAFT 就派实现任务，是本框架里最容易犯、代价最大的错误。A1 在这一步的职责就是拦住它。

### 第 4 步 · Q1 检查可验收性（1 条消息）

```
本周任务中，以下几条我暂时想不出机器验收命令：
- <任务> — 建议改成：<可验收的表述>
或
- <任务> — 确实无法机器验收，需要走 H2 人类品味评审，请人类排期
```

**想不出验收命令的任务不许进 Sprint。** 这不是形式主义：一个说不清怎么算做完的任务，交给 Bot 一定会变成无限期的挣扎。

### 第 5 步 · P0 排序与分派（1 条消息）

考虑三个约束：

| 约束 | 说明 |
|---|---|
| **车道不冲突** | 同一时间段内，两个任务不许写同一批文件 |
| **全局锁不冲突** | 需要同一把锁的任务串行排 |
| **每 Bot 同时只有 1 个 IN_PROGRESS** | Grok Bot 一次只能跑一个计算机任务，多派没用还会让它混乱 |

### 第 6 步 · 散会，P0 写任务信封

**群聊里不写任务信封。** 群聊只定"做什么、谁做、什么顺序"。
八段信封由 P0 会后逐个写成文件，走 `/sop-task-envelope`。

## 3. 容量规划（现实一点）

| 单位 | 定义 |
|---|---|
| 1 个"工作会话" | 一个 Bot 从接单到提 PR，约 1–3 小时 |
| 1 个 Bot 每天 | 1–2 个工作会话（要留出心跳、评审、返工的时间） |
| 1 个 Bot 每周 | **5–8 个工作会话** |

**每周产能 = 实现型 Bot 数 × 6 × 0.6**

那个 0.6 是返工系数。第一次做 Sprint 规划时你会觉得它太悲观，两周后你会觉得它太乐观。

**规划量不许超过产能的 80%。** 剩下 20% 留给：安灯、返工、突发的环境问题。排满的 Sprint 一定会延期，而延期的 Sprint 会让所有的进度数据失去意义。

## 4. 任务粒度

| 判据 | 说明 |
|---|---|
| 一个工作会话能做完 | 做不完就拆 |
| 一条验收命令能验 | 需要三条命令 = 三个任务 |
| diff 不超过 400 行 | 超了说明范围太大，评审者会失去判断力 |
| 只碰一个车道 | 跨车道 = 拆成两个任务 + 一个契约 |

> **拆不动怎么办？** 如果一件事天然拆不开（比如"实现 ECS 内核"），那就先派一个**探路任务**：
> 花一个会话产出设计草案和接口定义，不写实现。下周再按接口拆实现任务。
>
> 这比让一个 Bot 闷头做五天要好得多——五天后你得到的很可能是一个方向就错了的大 PR。

## 5. Sprint 中途的变更

| 情况 | 处理 |
|---|---|
| 人类改了优先级 | P0 可以中止未开始的任务，重排。已开始的**做完再说** |
| 拉了安灯 | 全线停止接新任务，直到 CLOSED |
| 某任务发现比预期大 3 倍 | 立刻停手，写阻塞报告，P0 重新拆分。**不许硬做** |
| 有 Bot 空闲 | P0 从 backlog 补派。**Bot 不许自己找活干**（宪法第六条） |

---

## 6. 会议纪律

1. **超过 30 条消息 = 规划失败。** 说明准备不足（P0 没提前整理状态）或者在群里做本该异步做的事。
2. **技术方案讨论超过 3 轮 → 转 ADR。** 群聊不是设计场所。
3. **每条发言标注类型**：提议 / 提问 / 裁决 / 通报。
4. S1 会后写 `board/minutes/<date>.md`，只记四样：**决定了什么 / 谁负责 / 什么时候前 / 依据是什么**。
